# FG C4 System Map

Используй этот skill, чтобы собирать и обновлять архитектурные карты FG как рабочие артефакты принятия решений, а не как абстрактные диаграммы.

Не используй его для:

- однофайловых рефакторингов
- чисто стилистических задач
- локальных исправлений без архитектурного влияния
- тривиальных переименований
- патчей кода

Если задача локальная или сводится к патчу, откажись явно:

`Это не требует C4-картирования. Существенного архитектурного scope здесь нет.`

## Уровень детализации

Начинай с наименьшего полезного уровня:

1. `System Context`
2. `Container`
3. `Component` только если это действительно нужно

По умолчанию сначала выбирай `System Context` или `Container`.

Не переходи к `Component`, если границы `Container` ещё не ясны.

`Component` разрешён только если одновременно верно всё:

- scope уже явно ограничен одной внутренней подсистемой
- границы `Container` уже подтверждены repo evidence
- задача требует именно внутреннего ownership/contracts mapping внутри этой подсистемы

Если есть сомнение между `Container` и `Component`, выбирай `Container`.

## Обязательные входы

До любых структурных выводов собери:

- exact anchors из repo
- целевую область
- текущую структуру
- владельцев и ответственности
- входящие интерфейсы
- исходящие интерфейсы
- dependency surfaces
- runtime write / effect surfaces, если они архитектурно важны
- поток данных
- риски или неоднозначность

Если anchors недостаточно, верни только `evidence gap`.
Не выдумывай отсутствующую структуру.

## FG-фокус

Держи карту привязанной к FG:

- frontend на React
- Compact vs Expanded split
- chart engine boundaries
- backend на Node / Express
- Django / Celery news pipeline
- Redis / MySQL roles
- Telegram Bot / MiniApp
- интеграции с OpenAI

## FG-правила

- по умолчанию пиши по-русски
- используй English только для file paths, code identifiers, exact anchors, status values и точных upstream/library terms, если перевод снижает точность
- не смешивай русские и английские narrative labels внутри одного раздела
- всегда указывай owner для каждого блока
- всегда указывай responsibility для каждого блока
- всегда указывай направление зависимостей
- всегда указывай contract surface
- всегда указывай failure sensitivity, если это важно
- не схлопывай shell, data-flow и runtime ownership в одного вымышленного owner
- предпочитай ясность полноте
- держи карту читаемой для человека
- отказывайся от патчей кода

## Правила вывода

- не делай структурных утверждений без anchors из repo
- сначала тезис, потом компактная группа anchors
- не повторяй одну и ту же цепочку anchors без новой смысловой нагрузки
- выбирай самый высокий уровень, который уже отвечает на вопрос
- если верхнеуровневые границы неясны, остановись и скажи это прямо
- различай interfaces, dependency surfaces и runtime effects
- interfaces = external or cross-boundary contract surfaces
- dependency surfaces = то, на что блок опирается
- runtime effects = state writes или chart runtime mutations, если они архитектурно важны
- не называй внутренние runtime writes `outbound interfaces`, если это не внешний контракт
- предпочитай простые архитектурные формулировки сложным jargon-heavy склейкам
- пиши так, чтобы текст читался как карта системы, а не как внутренний handoff log
- не переходи к планированию реализации

## Структура ответа

Используй ровно эту структуру:

### 1. Область

Коротко зафиксируй целевую область.

### 2. Использованный уровень

Используй один из:

- `System Context`
- `Container`
- `Component`

Если выбран `Component`, отдельно объясни, почему верхние уровни уже достаточно ясны.

### 3. Текущая структура

Покажи только те блоки, которые нужны для текущей области.

### 4. Владельцы и ответственности

Для каждого блока укажи:

- owner
- responsibility

### 5. Входящие интерфейсы

Перечисли только входящие external or cross-boundary contract surfaces в пределах выбранной области.

### 6. Исходящие интерфейсы

Сначала перечисли исходящие interfaces: только external or cross-boundary contract surfaces.
Затем отдельно укажи dependency surfaces: на что блок опирается.
Не относись к внутренним runtime writes как к interfaces.

### 7. Сводка потока данных

Коротко опиши главные направления зависимостей и движения данных.
Если для выбранной области важны runtime effects, выдели их отдельным подпунктом внутри этого раздела.

### 8. Риски / неоднозначность

Укажи:

- неясные границы
- недостающие anchors
- чувствительные к отказам границы, если они есть

### 9. Рекомендуемый следующий срез

Дай ровно один следующий срез.
Он должен быть минимальным и архитектурно значимым.

## Проверка качества

Перед финализацией проверь:

- нет архитектурной воды
- нет смешения русских и английских narrative labels
- нет повторяющихся цепочек anchors без новой смысловой нагрузки
- нет преждевременного перехода в `Component`
- не смешаны interfaces, dependencies и runtime effects
- нет углубления в `Component`, если верхние границы не определены
- результат читается как рабочий архитектурный артефакт FG
